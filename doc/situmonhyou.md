> **【保留】2026-09-18時点の注記**
> 整骨院版アプリの着手は、JavaScript制作にもっと慣れてからに変更した。
> 理由：現状はJS初学者であり、父親への聞き取りを待つ間に学習・制作の手が止まってしまうため。
> 現在の学習プロジェクトは `README.md` / `doc/apuriangenkei.md` の通り、汎用的な「仕事の在庫管理」として架空データで進める。
> このファイルは、将来整骨院版に着手する際の聞き取り計画としてそのまま保持する。

## 前提

- このアプリは JavaScript 学習を目的とした作品であり、実運用は目指さない
- 父は現在、在庫管理を行っていない（目で見て足りなそうなら発注する規模）
- 消費期限のある物品は無い
- Excel 連携は行わない。データはブラウザの localStorage に保存し、CSV エクスポートのみ持つ（インポートは v0.1 では対象外）
- 完成後、父に **1日程度試用**してもらい、フィードバックを受けて終了する

## 聞き取りの目的

運用方法を確かめるためではなく、次の3つを得るため。

1. **種データ**：父が画面を開いたとき「自分の院の棚だ」と感じられる実品目と数字
2. **試用計画**：いつ・どの端末で・何をしてもらうか
3. **検証したい仮説の材料**：「業務を覚えていなくても画面を見れば次の行動が分かる」という原案の主張を、在庫管理をしていない父で試すための情報

- 所要時間：20〜30分、雑談のつもりで
- 必ず取りたいもの：セクション1（種データ）、セクション4（試用の段取り）
- 可能なら：**棚の写真**、納品書や卸のカタログ

## 1. 種データ収集（最重要）

> アプリに最初から入っている品目リストの元になる。棚を見せてもらいながら聞くのが最も早い。

- [ ] 消耗品として置いてあるものを全部挙げてもらう（棚の写真を撮る）
  - 例：テープ、包帯、湿布、電極パッド、消毒液、ペーパー類、施術着、事務用品
- [ ] それぞれの数え方の単位は？（巻／箱／枚／本／袋）
- [ ] 今だいたいどれくらいある？（正確でなくてよい、感覚値）
- [ ] 「これくらいになったら頼む」という目安はある？（個数 or 「あと何日分」）
- [ ] 切れると一番困る順に3つ挙げるなら？
- [ ] 逆に、切れても数日は平気なものは？

**→ 決まる設計項目**
- 種データ（`items` 配列）の中身：品目名・単位・初期在庫・発注点
- 発注点は品目ごとに持つ（一律「5以下」は廃止）
- 「要対応」を上に出すときの並び順（重要度）

## 2. 発注の実務

> 状態「発注済み」と操作「入荷した」の設計に使う。詳細に聞く必要はない。

- [ ] どこから買う？（医療卸／メーカー直／Amazon・楽天／薬局）品目で違う？
- [ ] 注文方法は？（電話／FAX／業者が来たとき／Web）
- [ ] 頼んでから届くまでだいたい何日？
- [ ] 定期便・自動補充になっているものはある？

**→ 決まる設計項目**
- 発注先を品目に持たせるか（種データ表の「発注先」列で足りるならそれで十分）
- 定期便の品目は種データから外すか、「要発注」判定の対象外にするか
- リードタイムが短ければ「入荷予定日超過→要確認」は不要と確定

## 3. 今の判断のしかた

> 「在庫管理をしていない」状態を責めずに聞く。原案の判定ルールが現場の感覚とどうずれるかを知るため。

- [ ] 「そろそろ頼まなきゃ」と気づくのはどんなとき？（棚を見て／使い切って／業者が来て）
- [ ] 気づいてから頼むまでに間が空くことはある？ その間、覚えておく方法は？
- [ ] 過去に切らして困ったことはある？（患者さんへの影響が出たことは？）
- [ ] 頼んだつもりで頼んでいなかった、二重に頼んだことはある？
- [ ] 在庫管理をしていないのは「必要ないから」？「面倒だから」？

**→ 決まる設計項目**
- 「発注済み」状態を持つ意味（頼んだかどうかを覚えておく負荷をアプリに移す）
- 試用で最初に見せるべき状態（切らした経験がある品目を「要発注」で出す等）
- フィードバック質問の重点（面倒さが理由なら操作の手数に注目する）

## 4. 試用の段取り

> 「使ってみて」と渡すだけでは何も返ってこない。ここで具体的に決める。

- [ ] スマホ・タブレット・PC、どれで開いてもらうのが自然？
- [ ] 1日のうち、いつなら触れる？（開院前／昼休み／閉院後）
- [ ] 1日で何回くらい開いてもらえそう？（朝と夜の2回、など）
- [ ] 試用日はいつにするか（父の都合の良い日）
- [ ] 終わった後、感想を聞く時間を30分もらえるか

**→ 決まる設計項目**
- 画面幅の前提（スマホなら縦1列、要対応が最上部）
- 配布方法（GitHub Pages の URL をスマホで開く想定。`file://` は避ける）
- 試用シナリオ（下記）

### 試用シナリオ案（聞き取り後に確定）

1. 開いて「今日頼むべきものは何か」を答えてもらう
2. 「○○を△個使った」として在庫を減らしてもらう
3. 要発注になった品目を「発注済み」にしてもらう
4. 「届いた」として入荷操作をしてもらう
5. 最後に CSV エクスポートを押して、ファイルを送ってもらう（操作履歴の回収）

## 5. 試用後のフィードバック質問（事前に用意しておく）

> 「使いやすかった？」は聞かない。「まあまあ」しか返ってこない。

**画面を見て**
- [ ] 最初に開いたとき、何をすればいいと思った？
- [ ] 「要発注」のラベルと色の意味は、説明なしで分かった？
- [ ] 上に出ている品目と下に出ている品目の違いは分かった？

**操作して**
- [ ] 在庫を減らす操作は迷わずできた？ どこで迷った？
- [ ] 「発注済み」にする操作の意味は分かった？
- [ ] 押すのが面倒だと感じた操作はあった？

**全体**
- [ ] もし自分の院にこれがあったら、朝に開くと思う？ 開かないなら何が理由？
- [ ] 紙やノートと比べて、良かった点・悪かった点は？
- [ ] 品目や数字は実際の棚と合っていた？ 違和感のあったものは？

**回収するもの**
- [ ] エクスポートした CSV（操作履歴）
- [ ] できればスマホ画面のスクリーンショット（実際に見た状態）

## 聞き取り時のコツ

- 「どんな機能が欲しい？」は聞かない
- 直近の具体的な一回（最後の発注、最後に切らしたとき）を掘る
- **棚を実際に見せてもらう・写真を撮る**。セクション1がこれで大半終わる
- 納品書・卸のカタログがあれば品目名の正式な表記が取れる
- 答えを設計用語に変換しない。父の言葉のまま書き留める

## 原案との差分（聞き取り前に確定している分）

| 原案の前提 | 学習作品としての採否 | 理由 |
|---|---|---|
| Excel が正本、Web は表示 | 不採用 | Excel が存在しない。アプリ自身が種データを持ち localStorage に保存 |
| 品目共通の発注点・5以下で緊急 | 変更 | 品目ごとの発注点にする。「緊急発注」状態は落とす |
| 発注済み→入荷待ち→予定日超過で要確認 | 縮小 | 状態は `在庫良好` / `要発注` / `発注済み` の3つ。超過判定は落とす |
| 消費期限 | 対象外 | 該当物品なし |
| 現在庫を誰かが更新し続ける | 対象外 | 1日の試用で完結。継続運用は目指さない |
| PC 画面＋印刷 | 変更 | 端末はセクション4で決める。印刷は CSV エクスポートに置き換え |
| CSV インポート（復元） | v0.1 対象外 | FileReader・CSV パースは次バージョン以降 |
